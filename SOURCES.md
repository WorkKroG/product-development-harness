# Sources and provenance

Prepared 2026-09-05; adapted for this public repository on 2026-09-06.
This is a public summary. The owner's original transfer package, including private immutable
source references, is retained locally in ignored `.local-handoff/` and is not a repository dependency.
Observations below are historical reports, not independently reproducible public runtime evidence.

## S1. Original product-development-cycle

The owner's existing seven-file skill is preserved unchanged under
[baseline/product-development-cycle](baseline/product-development-cycle/SKILL.md).
[BASELINE.sha256](BASELINE.sha256) identifies each file. The first local bootstrap commit preserves
this snapshot; it does not reconstruct earlier history. Ownership/licensing of redistributed
materials must be established before public distribution; do not invent a license.

## S2. Prior product delivery process

The owner's previous product project supplied experience with coordinator roles, work items,
independent review, exact-head evidence, handoff prompts and mechanical documentation checks.
Nine historical process/checker files are retained in the local private source package.
No private repository URLs, source content, task IDs or commit references are required to use
the public specification. The snapshot establishes historical context, not current project state.

## S3. Owner decisions and observed coordination

The owner accepted the role hierarchy, native model matrix, manual merge, automatic transfer of
results and main-coordinator product approvals. Routine implementation does not require deep
technical owner approval. Delivery modules and lifecycle readiness gates are different concepts.
An observed platform denial of forwarded approval motivated explicit separation of scope mandate,
account access and platform permission. Handoff/monitoring acknowledgement was observed in the
source project; uninterrupted autonomous operation in every Codex environment was not proven.

## S4. Independent plan review in the source project

A historical independent review caught duplicate accepted work, omitted permission requirements,
unnecessary status changes and inaccurate behavior descriptions. The reviewed plan and evidence
remain in the private provenance package. This motivates review against actual requirements and
code, but does not prove whole-module FINAL or the future harness's end-to-end behavior.

## S5. Skill format and runtime constraints

The local skill-creator and [Build skills](https://learn.chatgpt.com/docs/build-skills) were read
2026-09-05. They informed the SKILL.md/references/assets/scripts structure, version identity and
installation checks. The future installer must verify actual discovery in the target environment.
Native task/message/wait/automation/model fields were available in the source desktop context;
availability in other clients and versions must be checked, not assumed.

## S6. Staged architecture

On 2026-09-06 the owner accepted early planning for future loads, staged architectural
implementation and reconsideration before scaling. Five stages and the 10/100-thousand-user
milestones are project conventions, not universal capacity standards. Prototype code may be
discarded without making a rewrite mandatory; preserve validated knowledge and necessary data.

## S7. Light viability before Journey

On 2026-09-06 the owner requested a short market, competition and economics estimate between
Positioning and Journey for deciding whether and how to proceed. The original skill's heavier
early Gate 4.5 overlaps this purpose. The specification replaces it with light Gate 3.5 and
retains Gate 8 for investment-proportionate refinement, reusing existing research.
The installed skill and historical baseline remain unchanged.

## Limits

The full new-product lifecycle, proposed E01–E41 scenarios, independent review of this specification,
whole-module FINAL, production release and clean-environment installation have not been demonstrated.
